# Portainer: установка с автоматическим обновлением mCMS

[К оглавлению](README.md) · [English](../en/portainer-auto-updates.md) · [Обновления и откат](operations.md)

Руководство рассчитано на **Portainer CE + Docker Standalone**. Здесь описаны два сценария: установка нового mCMS с релизными Docker-образами и **перевод существующего Git Stack без потери данных**. Для обычного запуска mCMS API-токен Portainer не нужен: он требуется только для автоматического обновления **ядра**. Автоматическое обновление ZIP-модулей/тем использует другой механизм.

## 1. Выберите режим развёртывания

| Режим | Compose path | Как обновляется ядро |
|---|---|---|
| Git-сборка | `portainer-stack.yml` | Администратор выполняет Git Re-pull/Redeploy с пересборкой образов; сам Core не обновляется |
| Релизные образы GHCR | `portainer-release-stack.yml` | При настроенном Portainer API компонент `mcms-updater` проверяет выпущенные GitHub Releases, создаёт резервную копию и запрашивает redeploy |

Для второго варианта `app`, `web` и `updater` используют публичные образы `ghcr.io/mirivlad/mcms-app:stable` и `ghcr.io/mirivlad/mcms-web:stable`. Сначала проверьте [официальные релизы](https://github.com/mirivlad/mcms/releases) и наличие `mcms-images-ready.json` у нужного релиза. Событие публикации кода в `main` само по себе не означает, что готов новый стабильный релиз.

**Ограничение:** автоматически устанавливаются только новые стабильные **патч-версии того же major/minor** (например, 0.1.9 → 0.1.10). Переход 0.1.x → 0.2.0 и автоматический откат после неудачного redeploy не поддерживаются.

## 2. Новый сайт: создайте релизный Git Stack

1. В Portainer откройте **Stacks → Add stack → Repository**. Укажите название, например `mcms`, репозиторий `https://github.com/mirivlad/mcms`, ссылку ветки `refs/heads/main` и **Compose path `portainer-release-stack.yml`**. Для существующего сайта вместо этого выполняйте [раздел 3](#3-переход-существующего-сайта-с-git-stack).
2. В Environment variables задайте как минимум `MCMS_DB_PASSWORD` и **отличающийся** `MCMS_DB_ROOT_PASSWORD`. Не используйте примеры паролей из документации. Для внешнего reverse proxy стандартное HTTP-подключение — `127.0.0.1:8188`; установите домен и HTTPS в своём Nginx/Caddy, передавайте `Host` и `X-Forwarded-Proto`.
3. Явно добавьте `MCMS_IMAGE_TAG=stable`. Добавьте **`MCMS_DB_IMAGE` с digest**, а не только плавающим тегом MariaDB (см. раздел 4). Не удаляйте остальные настройки почты/базы, если они уже заданы.
4. Выполните deploy, дождитесь здоровой MariaDB и откройте сайт: `/install` предложит создать администратора. Создайте и скачайте полную резервную копию через **Администрирование → Резервные копии**.
5. Создайте токен и задайте параметры API (раздел 5), затем включите обновление Core в `/admin/updates`. До настройки API сайт работает нормально, но автоматического обновления ядра **не будет**.

## 3. Переход существующего сайта с Git Stack

**Не создавайте второй Stack для той же базы и не удаляйте существующий.** Все действия выполняются внутри текущего Stack с **прежним именем**: от имени Compose-проекта зависят имена Docker-томов.

1. В mCMS откройте **Администрирование → Резервные копии**, создайте ZIP и **скачайте его на другое устройство**. Сохраните текущие переменные окружения и настройки Stack в безопасное место (в них секреты). При критичном сайте заранее сохраните совместимый текущий Docker-образ/исходный Git-коммит для ручного отката.
2. В Portainer откройте **Stacks → ваш существующий Stack → Edit Git settings** (пункты могут отличаться по версии Portainer). Оставьте тот же репозиторий, ветку `main`, **имя Stack** и все Environment variables. Измените только путь Compose на `portainer-release-stack.yml`.
3. Отключите конкурирующее автоматическое GitOps polling/forced redeploy: Core-обновлятор должен самостоятельно решать, когда можно выполнить redeploy после резервирования и проверки версии.
4. Установите `MCMS_IMAGE_TAG=stable` и `MCMS_DB_IMAGE` с **digest именно согласованного образа MariaDB**; сохраните настройки API из раздела 5. Проверьте старые имена томов (см. ниже).
5. Запустите **Pull and redeploy / Re-pull image** существующего Stack, **не отмечая удаление volumes**. Дождитесь загрузки `app`, `web`, `updater` и здоровья MariaDB. Откройте админку, проверьте вход, страницы, картинки, заказ и бэкапы.

**Проверка томов до изменений** (на Docker-хосте):

```bash
for c in mcms-db-1 mcms-app-1 mcms-web-1 mcms-mail-1; do
  docker inspect "$c" --format '{{.Name}} {{range .Mounts}}{{.Name}}:{{.Destination}} {{end}}'
done
```

Имена контейнеров приведены для Stack `mcms`; на другом сайте их префиксы будут отличаться. Обычно томов **шесть** (`db_data`, `modules_data`, `themes_data`, `backup_data`, `mail_queue`, `dkim_data`), а контейнеров **пять** — это нормально. Нельзя использовать `docker compose down -v`, удалять volumes или менять имя Stack во время перехода. Если **Compose path** не редактируется, остановитесь и сначала уточните процедуру для вашей версии Portainer, а не создавайте новый Stack на той же БД.

## 4. Закрепите MariaDB и образ приложения

В **Stack → Environment variables**:

```dotenv
MCMS_IMAGE_TAG=stable
MCMS_DB_IMAGE=mariadb:11.4@sha256:<64_символа_digest_образа>
```

Узнать опубликованный *manifest digest* уже загруженного образа можно на **Docker-хосте**:

```bash
docker image inspect mariadb:11.4 \
  --format '{{range .RepoDigests}}{{println .}}{{end}}'
```

Пример возвращаемого имени — `mariadb@sha256:...`. Используйте **его 64-символьный digest** вместе с версией `mariadb:11.4@sha256:...`; не путайте RepoDigest с локальным `Image ID`, который показывает `docker inspect <container> --format '{{.Image}}'`. Убедитесь, что digest соответствует версии и архитектуре вашего рабочего образа. Изменение digest по сути является отдельным обновлением MariaDB и не должно сопровождать автоматическое обновление CMS.

Обновлятор проверяет оба значения: `MCMS_IMAGE_TAG` должен быть **ровно** `stable`, а `MCMS_DB_IMAGE` должен быть закреплён по SHA-256. Без этого автоматическое обновление Core будет отклонено.

## 5. Настройте Portainer API (только для автообновления Core)

1. Зайдите в Portainer под отдельной учётной записью, которой разрешено управлять **только нужным Stack**, насколько это допускает конфигурация Portainer. В **My account → Access tokens → Add access token** создайте токен, например `mcms-updater`. Сразу сохраните секрет: повторно он не показывается. Не добавляйте его в публичный репозиторий, снимки экрана и логи.
2. Узнайте **Stack ID**: откройте этот Stack в Portainer и посмотрите его числовой идентификатор в адресе/деталях (часто путь `/stacks/37`). **Число в имени контейнера** `mcms-app-1` и номер Docker-тома не являются Stack ID.
3. Узнайте **Environment / Endpoint ID**: зайдите в **Environments**, откройте нужное Docker-окружение, найдите ID в его деталях или URL выбранного окружения. Например, в пути вида `#!/2/docker/dashboard` число **2** — ID окружения. Это не Stack ID.
4. Выберите URL Portainer, доступный **из контейнера updater**, строго по HTTPS с доверенным TLS-сертификатом. Адрес `https://localhost:9443` **не работает из контейнера** как адрес хоста. URL должен указывать на ваш Portainer, а не mCMS.
5. В **Environment variables того же Stack** добавьте:

   ```dotenv
   MCMS_PORTAINER_URL=https://portainer.example.com
   MCMS_PORTAINER_API_KEY=ptr_<секретный_токен>
   MCMS_PORTAINER_STACK_ID=<числовой_ID_Stack>
   MCMS_PORTAINER_ENDPOINT_ID=<числовой_ID_Docker_окружения>
   ```

6. Сохраните Stack и примените изменения, чтобы контейнер `updater` получил переменные. Эти четыре значения передаются **только сервису `updater`**, а не публичному контейнеру `app`. Однако пользователи с доступом к настройкам Stack в Portainer могут видеть его переменные; ограничьте этот доступ.
7. В интерфейсе самой mCMS откройте **Администрирование → Обновления** (`/admin/updates`) и включите **Core**. Переключатели обновления модулей и тем независимы.

### Зачем API вообще нужен?

`mcms-updater` не получает Docker socket. Он проверяет актуальный GitHub Release и `mcms-images-ready.json`, убеждается в совместимости версии, сверяет **точно тот Stack и окружение**, наличие `stable` и закреплённой MariaDB, создаёт ZIP текущего сайта и только затем обращается к **Portainer REST API** за Git redeploy. Portainer скачивает новые `app`/`web` образы и пересоздаёт контейнеры с **теми же томами**. Перед запросом обновлятор записывает состояние в приватное хранилище, поскольку при redeploy будет перезапущен и он сам.

Включённый в mCMS переключатель **сам по себе не означает**, что весь механизм настроен. Если API-параметры пустые или Stack работает по `portainer-stack.yml`, Core **не обновится автоматически**, даже если обновления модулей работают.

## 6. Проверка после переключения

Убедитесь, что сервисы `app`, `web`, `updater`, `db` и `mail` работают, затем на Docker-хосте:

```bash
# Фактическая версия ядра (замените префикс контейнера, если Stack называется иначе)
docker exec mcms-app-1 php -r \
  'require "/var/www/html/src/Core/Version.php"; echo \\MCMS\\Core\\Version::VERSION, PHP_EOL;'

# Ошибки фонового обновлятора
docker logs --tail=100 mcms-updater-1
```

Проверяйте в **Portainer → Stacks → ваш Stack**, что Compose path равен `portainer-release-stack.yml` и контейнеры `app`/`web` используют `ghcr.io/mirivlad/mcms-*:stable`, а не локальные имена `mcms-app`/`mcms-web`.

Служба автоматически проверяет обновления примерно **раз в 6 часов** (`MCMS_UPDATE_INTERVAL_SECONDS=21600`). Сообщение «No eligible automatic extension updates» относится к **расширениям**, оно **не подтверждает** готовность автоматического обновления ядра. Команда `php spark mcms:updates:run` **не является безопасной диагностикой**: при включённом Core она может действительно запустить redeploy.

### Если не обновляется

- Отсутствует `mcms-images-ready.json` у релиза → подождите завершения публикации Docker-образов.
- URL Portainer не открывается из `updater` или TLS-сертификат не доверен → исправьте DNS/HTTPS/маршрутизацию; отключать TLS-проверку нельзя.
- Ошибка API 401/403 → проверьте права и срок действия токена.
- В Stack выставлен не `stable`, не тот ID Stack/Endpoint либо не закреплена MariaDB → исправьте значения, примените Stack.
- Целевой релиз меняет major/minor → обновите вручную по процедуре [отката и восстановления](recovery.md).
- Сайт остался на старой версии → проверьте журнал `updater`, состояние Core update в админке и релизные образы. Не отправляйте API-запрос redeploy повторно, пока не выяснили, не завершилось ли первое обновление.

## 7. Резервирование и откат

Перед первым переходом и каждым ручным обновлением **скачивайте полный ZIP за пределы сервера**. Автоматический Core-обновлятор создаёт локальную защитную копию, но пока **не гарантирует** автоматический откат образов и миграций БД. Для аварийного отката понадобятся предыдущие совместимые образы/тег, полная копия сайта **от прежней версии Core** и доступ к Portainer. Подробная процедура: [Резервные копии, восстановление и откат](recovery.md).

**Безопасность:** Portainer API-токен даёт полномочия на управление инфраструктурой. Настраивайте минимальные доступные права, храните токен только в приватных переменных Stack, ограничивайте администраторов и периодически меняйте ключ.
